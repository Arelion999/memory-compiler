# Настройка memory-compiler в Kimi Work

[English](kimi-work-setup.en.md) · **Русский**

Kimi Work (десктоп, движок daimon) подключается как плагин: MCP-сервер,
скил memory-autopilot и хуки живут в одном пакете, рантайм исполняет хуки
сам. Инструкция для Windows/macOS/Linux.

## 1. Запуск сервера

**Локально (Docker):**
```bash
git clone https://github.com/Arelion999/memory-compiler.git
cd memory-compiler
cp .env.example .env
# Заполнить MC_API_KEY и MC_ENCRYPT_KEY в .env
docker-compose up -d
```

**Проверка:**
```bash
curl http://<хост>:8765/api/health
# {"status": "ok", ...}
```

Сервер может жить на другой машине (NAS, сервер в локальной сети) — плагину
нужен только URL и ключ.

## 2. Создание плагина и подключение MCP

Kimi Work подключает MCP-серверы через плагины личного рынка. Создайте
каталог плагина (вне репозитория memory-compiler, например в своём каталоге
инструментов):

```json
// <каталог-плагина>/kimi.plugin.json
{
  "name": "memory-compiler",
  "version": "0.1.0",
  "description": "Personal knowledge base memory-compiler",
  "skills": "./skills/",
  "mcpServers": {
    "memory-compiler": {
      "url": "http://<хост>:8765/mcp/",
      "headers": { "X-Api-Key": "<MC_API_KEY>" }
    }
  },
  "sessionStart": { "skill": "memory-autopilot" }
}
```

Скопируйте скил в плагин (он понадобится и дальше):

```bash
mkdir -p <каталог-плагина>/skills/memory-autopilot
cp skills/memory-autopilot/SKILL.md <каталог-плагина>/skills/memory-autopilot/SKILL.md
```

Зарегистрируйте плагин в личном рынке и установите:

```bash
# Регистрация (путь к kimi-daimon зависит от установки клиента)
kimi-daimon kimi-plugin register-personal <каталог-плагина> --share-dir <daimon-share>
```

Затем: **Настройки → Плагины → вкладка «Персональные» → установить**. Демон
применяет установку к активным сессиям — перезапуск клиента не нужен.

Поле `sessionStart` — нативная замена SessionStart-хука: рантайм сам
показывает скил memory-autopilot в начале каждой сессии.

---

## 3. Установка скила memory-autopilot

Скил автоматизирует весь цикл работы с памятью: ищет контекст, определяет
проект, выбирает tool, сохраняет результат.

Kimi Work читает пользовательские скиллы из `~/.agents/skills` — положите
туда копию:

```bash
mkdir -p ~/.agents/skills/memory-autopilot
cp skills/memory-autopilot/SKILL.md ~/.agents/skills/memory-autopilot/SKILL.md
```

Копия внутри плагина (шаг 2) отвечает за автозагрузку на старте сессии,
копия в `~/.agents/skills` — за срабатывание по триггерам в любом рабочем
каталоге. Обе одинаковые, синхронизируйте при обновлении.

**Настройка проектов:** отредактируйте таблицу «Определение проекта» в
SKILL.md под свои проекты.

---

## 4. AGENTS.md рабочих каталогов

Глобального AGENTS.md у Kimi Work нет — клиент читает AGENTS.md рабочего
каталога. Добавьте правило в шапку AGENTS.md каждого проекта, где работает
ассистент:

```markdown
# <проект>

🛑 ПЕРВОЕ ДЕЙСТВИЕ ЛЮБОЙ ЗАДАЧИ — память: скил memory-autopilot (или сразу
start_task/search из инструментов плагина memory-compiler). В Kimi Work
хуков-напоминал нет до установки mc_guard (шаг 5) — напоминать некому,
обязанность целиком на модели.
```

После установки mc_guard (шаг 5) этот пункт остаётся полезным как первый
рубеж, а гейт становится вторым.

## 5. Hooks: гейт памяти mc_guard

Скил — мягкий канал: он срабатывает, когда модель его вызывает. Жёсткий
канал — хуки: Kimi Work исполняет `hooks`, объявленные в манифесте плагина,
сам (события SessionStart, UserPromptSubmit, PreToolUse, Stop, PostToolUse и
другие; PreToolUse умеет блокировать вызов с причиной).

Сторож `hooks/mc_guard.py` из репозитория memory-compiler умеет работать с
Kimi Work. Одна команда из каталога репозитория:

```bash
python hooks/install.py --client=kimiwork
```

Инсталлятор: копирует `mc_guard.py` и `mc_guard.env` (адрес сервера и ключ —
редактируйте его после установки) в `<каталог-плагина>/hooks`, прописывает
7 хуков в `kimi.plugin.json` и бампит версию плагина. После этого:

1. перерегистрируйте плагин (`kimi-plugin register-personal`, как на шаге 2);
2. в клиенте нажмите **обновить** у плагина во вкладке «Персональные».

Что включено в хуки плагина:

| Событие | Подкоманда | Что делает |
|---|---|---|
| `SessionStart` | `session_start` | стартовый контекст из базы |
| `UserPromptSubmit` | `freshness` | записи других сессий + напоминание про память |
| `PreToolUse` | `nul_guard` | блок редиректа в `nul`/`con` (Windows) |
| `PreToolUse` | `gate` | **не пускает на инфраструктуру без чтения базы 15 мин** |
| `PreToolUse` | `session_arg` | передаёт id чата серверу (свежесть контекста) |
| `Stop` | `stop` | страховка: не дать закрыть сессию без finish_task |
| `PostToolUse` | `mark` | отметка «база прочитана» (снимает гейт) |

Имена инструментов в Kimi Work выглядят как `mcp__plugin-<плагин>_<сервер>__<tool>`
— mc_guard сводит их к обычному виду `mcp__<сервер>__<tool>` сам, матчеры
прописывать не нужно. Тесты: `MC_GUARD_CLIENT=kimi python hooks/test_mc_guard.py`.

## 6. Проверка работы

В **свежем чате** Kimi Work:

1. **Скил в индексе:** в списке скиллов сессии должен быть `memory-autopilot`.
2. **MCP доступен:** «проверь доступность базы знаний» → вызов `list_projects`.
3. **Гейт (после шага 5):** попросите вызвать любой инфраструмент, не читая
   базу, — вызов будет заблокирован с инструкцией сначала сделать `search`.
   После `search` повторный вызов пройдёт. Проверка видна в журнале
   `~/.kimi-code/hooks/mc_hooks.log` (записи `gate.block` / `gate.pass`).
4. **Пробный цикл:** скажите факт («сервер X на площадке Y») — скил сохранит
   через `save_lesson`; поставьте задачу — скил вызовет `start_task` и в
   конце `finish_task`.

## 7. Зависимости проектов

`start_task` автоматически подтягивает контекст из зависимых проектов:

```python
set_project_deps(project="client-a", depends_on=["work", "infra"])
set_project_deps(project="myapp", depends_on=["infra", "work"])
```

## 8. Что умеет Kimi Work

| Функция | Статус | Комментарий |
|---------|--------|-------------|
| MCP tools (все 50) | ✅ | Через плагин, Streamable HTTP |
| Скил memory-autopilot | ✅ | Автотриггер + `sessionStart` плагина |
| Hooks гейта (gate/stop/freshness) | ✅ | Нативно: `hooks` в манифесте плагина |
| Блокировка вызова с причиной | ✅ | `PreToolUse` + `permissionDecision: deny` |
| Авто-search_error при traceback | ✅ | Через скил (Фаза 0) |
| Подмена аргументов (`updatedInput`) | ⚠️ | Протокол поддерживает; mc_guard не полагается на неё — есть боковой канал `/api/session_hint` |

## Диагностика

**Инструменты плагина не появились?**
- Плагин установлен во вкладке «Персональные» (не только зарегистрирован)?
- Сервер жив: `curl http://<хост>:8765/api/health`
- Ключ в `headers.X-Api-Key` верный.

**Хуки не срабатывают?**
- После `install.py --client=kimiwork` плагин перерегистрирован И обновлён
  в клиенте? Хуки читаются из установленной копии, а не из исходников.
- Журнал: `tail -f ~/.kimi-code/hooks/mc_hooks.log` — там виден каждый
  запуск хука.
- `mc_guard.env` рядом с копией скрипта заполнен (`MC_API_URL`, `MC_API_KEY`).

**Гейт блокирует вечно?**
- Клапан есть: после двух блокировок подряд вызов пропускается (запись
  `gate.valve` в журнале). Если база недоступна — скажите об этом, не
  выдумывайте факты по памяти.
