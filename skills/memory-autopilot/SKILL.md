# Memory Autopilot

Память работает невидимо. Пользователь ставит задачу — ты сам решаешь, что искать,
что сохранять, куда класть и каким инструментом. Он не должен просить.

## Железные правила

1. **Только `mcp__memory-compiler__*`.** `mcp__memory` (create_entities, add_observations) — устаревшая система, не использовать НИКОГДА.
2. **Имена проектов в нижнем регистре.** Сервер нормализует сам, но единообразие помогает другим сессиям.
3. **Не хардкодить имена клиентов и проектов** — узнавать через `route_project()` / `list_projects()`. Это open-source-инструмент, утечки имён недопустимы.
4. **Запись обязана состояться.** Вызов не прошёл — не «ну ладно, потом»: см. `references/failed-calls.md`.

## Определение проекта

По порядку, до первого попадания:

1. Пользователь назвал проект явно — берём его.
2. `route_project(text=<сообщение>, cwd=<рабочий каталог>)` — сервер сам сверит `cwd` с `list_projects()`; совпал basename — вернёт score 100. Это самый частый случай.
3. Ранжирование по тексту сообщения из того же вызова: score ≥ 25 — берём топ-1.
4. Иначе `general`.

У пишущих инструментов `project` можно не указывать вовсе: сервер подставит проект,
с которым эта сессия уже работала, и назовёт его в ответе (v1.90.0). Явный проект
всё равно лучше — подстановка страхует от потери записи, а не заменяет выбор.

## Фаза 0: что это за сообщение

| Тип | Пример | Действие |
|-----|--------|----------|
| **Continuation** | «продолжим», «давай дальше», «что у нас по X» | `start_task(topic, project)` БЕЗ search: фраза из стопвордов, поиск вернёт мусор. Сервер распознает продолжение и отдаст активный контекст + последнюю сессию |
| **Задача** | «настрой nginx», «проверь доступность X» | Фаза 1 |
| **Проверка сущности** | «проверь X», «статус Y» | `search(<сущность>)` → контекст → выполнять |
| **Факт/информация** | «сервер X на Y», «пароль от Z: …» | сразу `save_lesson` / `save_secret` / `save_tracking` / `edit_article` |
| **Вопрос с контекстом** | «какой IP у X?», «как настроен Y?» | `search` / `get_context` / `read_article` |
| **Ошибка, traceback** | стектрейс, код ошибки | `search_error(error_text, project)` → Фаза 1 |
| **Простой вопрос, приветствие** | «что такое X?», «привет» | не триггерить |

## Фаза 1: старт задачи

Есть traceback — сперва `search_error(error_text, project)`. Затем определить проект
и вызвать `start_task(topic, project)`. Он вернёт похожие кейсы, активный контекст,
открытые вопросы, сроки на исходе, решения и runbooks — использовать всё это.

## Фаза 2: в работе

| Нужно | Вызов |
|---|---|
| Креды, пароли, IP, пути | `search("<сущность> доступы пароль")` → `read_article` (секрет расшифруется сам). **Не спрашивать пользователя** |
| Контекст по теме | `get_context(project, query)` |
| Похожая ошибка | `search_error(error_text, project)` |
| Текущая версия / деплой / конфиг | `get_current(project, entity)` |
| Документация по URL | `ingest(project, url)` |

**Правила поиска.** Пусто на латинице — попробуй кириллицу и наоборот. Содержимое
секретов не индексируется, искать по НАЗВАНИЮ сущности. Пусто с первого раза — дай
2–3 варианта (имя клиента, продукт, тип ресурса). Инструменты поиска ровно эти:
`search`, `search_by_tag`, `search_error`, `search_decisions`, `search_snippets`.

## Фаза 2.5: возвращаться в базу ПОСРЕДИ сессии

`start_task` загружает СНИМОК, и он стареет: параллельная сессия правит то же железо
и пишет туда же. Обязательные точки повторного обращения — даже если скил уже вызывался:

| Момент | Что делать |
|---|---|
| Собрался утверждать факт о чужой инфраструктуре — адрес, пароль, версия, как настроено, почему так | `search` ДО утверждения |
| Нужны креды, доступ, ключ | `search(project="all", "<сущность> доступы пароль")` → `read_article` |
| На железе не то, что ты ожидал | `search` по сущности + `get_active_context(project)`: почти наверняка это СДЕЛАЛА ДРУГАЯ СЕССИЯ и уже описала |
| Больше ~15 минут работы без базы, и снова лезешь на живое | `search` перед вызовом |
| Задача повернула на другую сущность | новый `search` по новой сущности |

**Изменения на железе, которых ты не делал, — сигнал, а не загадка.** Сначала спроси
базу «что тут делали», потом расследуй. Обратный порядок — повторный разбор уже
разобранного, с риском откатить чужую свежую правку.

**Запрещённые фразы без предварительного поиска:** «нет доступа», «у меня нет пароля»,
«запусти сам», «выполни вручную», «нужны креды». Доступы к инфраструктуре владельца
лежат в базе — это его база и его инфраструктура. Отказ допустим только после поиска
и пробного вызова, и в отказе надо показать, ЧТО именно проверено.

**Это подпёрто хуками.** `PreToolUse` не пускает на mikrotik / ssh / synology / 1c / ftp
и на удалённые команды в Bash, пока в сессии не было чтения базы за 15 минут;
`UserPromptSubmit` показывает записи других сессий; `Stop` блокирует ответ с «нет
доступа» без поиска. Гейт снимается одним `search` — не обходить его другим инструментом.

## Фаза 2.6: заметка по ходу (`session_note`)

Итог пишется в конце, а выясняется всё по дороге: работа после последней загрузки
контекста — медиана 25 минут, p90 101 (замер по 502 сессиям), и всё найденное за это
время для параллельной сессии не существует. `session_note(note, project)` — одна
строка в текущий блок журнала, без пересборки сводки, git и индексации.

Звать сразу, как появилось: причина найдена (задача ещё открыта); гипотеза НЕ
подтвердилась; на железе не то, что ожидал; решение принято по ходу; перед долгой
операцией (сборка, restore, прогон). Заметки вливаются в итоговый блок при
`finish_task` — дублировать их в `content` не надо.

Сервер сам напомнит, если по проекту идёт больше 25 минут без записи.

## Фаза 3: сохранение

Сперва проверь, не существует ли статья: `search(query=<тема>, project)`. Score > 35
на ту же тему — `edit_article(project, filename, content, append=true)`, иначе новая.

| Что сохраняешь | Инструмент |
|---|---|
| Был выбор между альтернативами | `save_decision` |
| Пошаговая инструкция | `save_runbook` |
| Баг с чётким фиксом | `save_from_template(bug)` |
| Настройка, деплой | `save_from_template(setup/deploy)` |
| Всё остальное | `save_lesson` |
| Новый пароль, ключ, cred | `save_secret` |
| Изменилась версия, конфиг, статус | `save_tracking` |
| Документация по URL | `ingest` |

Знаешь, при какой ошибке или на каком узле статья должна всплыть сама, — передай
`triggers` (`«ошибка: <дословно>»`, `«цель: <хост>»`, `«файл: <путь>»`). Факт получен
инструментом, а не выведен косвенно, — передай `verified`.

## Фаза 4: завершение

```
finish_task(topic, content, project, session_summary, open_questions)
```

**Вызывается ВСЕГДА, когда задача решена.** Не жди просьбы.

`content` — около 1500 символов обычного текста, до ~4000, когда тема неделимая.
Несколько тем — несколько статей: закопанный в чужой `content` разбор не всплывает
в поиске, потому что ранжируются заголовки. Почему именно столько, как отличить обрыв
генерации от битого JSON и что делать с упавшим вызовом — `references/failed-calls.md`.

## Фоновые действия

`start_task` / `search` / `search_error` — в начале, показать только релевантное.
`finish_task` / `save_*` — в конце, коротко подтвердить «Записано».
`route_project` / `list_projects` — молча, когда непонятно, куда класть.

**Не сохранять:** тривиальные ответы на общие вопросы, то, что уже есть в коде или
git-истории, временный контекст сессии (для него `session_summary`).

## Red Flags

| Мысль | Реальность |
|-------|------------|
| «Спрошу пользователя, какой проект» | `route_project(text, cwd)` |
| «Это не стоит сохранять» | Решал дольше двух минут — сохрани |
| «Сохраню потом» | Потом = никогда |
| «Допишу это в итог сессии» | Итог будет через час и без подробностей. `session_note` — сейчас, одной строкой |
| «Пользователь не просил сохранить» | Он и не должен. Это автопилот |
| «Контекст я загрузил в начале сессии» | Снимок устарел — Фаза 2.5 |
| «На железе что-то поменялось, надо разобраться» | Сперва спроси базу, кто и что менял |
| «Скажу, что нет доступа» | Сперва `search` + `read_article`. Доступы в базе |
| «Гейт заблокировал — обойду другим инструментом» | Гейт снимается одним `search` |
| «Компилер не ответил, запишу потом» | Повтори сейчас: первый вызов после рестарта падает всегда |
| «Вызов упал — скажу пользователю и пойду дальше» | Повтор → разбор класса отказа → только потом честное «не вышло» |
| «Вызов упал, повторю тем же payload» | Сначала определи класс: обрыв ≠ синтаксис ≠ обёртка |
| «Задача простая для finish_task» | Использовал `save_*` — вызови `finish_task` |
| «Захардкожу клиента в скил» | Это утечка. `route_project` |
